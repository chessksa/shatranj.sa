# تصميم توسيع لوحة إدارة مشروع الشطرنج

التاريخ: 2026-09-06

## الهدف

توسيع لوحة الإدارة الحالية لتصبح مركز إدارة كاملًا للاعبين والمشرفين والبطولات، مع الحفاظ على نظام Supabase الحالي وعدم كسر تسجيل الدخول أو اللعب أو البيانات الموجودة.

## نطاق التغيير

يشمل هذا التصميم أربعة محاور مترابطة:

1. إدارة اللاعبين: إضافة لاعب، تعديل بياناته، حظره، وحذفه نهائيًا.
2. إدارة المشرفين: مالك واحد بصلاحيات كاملة، ومشرفون بصلاحيات تشغيلية أقل.
3. إدارة البطولات: إنشاء بطولات عامة أو مقيّدة بدولة أو مدينة داخل دولة.
4. الأمان والتدقيق: نقل العمليات الحساسة إلى مسار خادمي آمن وتسجيل كل إجراء إداري.

## الوضع الحالي

- توجد لوحة إدارة عبر `admin.html` و`admin.js`.
- توجد صلاحيات حالية للحظر وفك الحظر وتعديل النقاط ومراجعة المباريات والبلاغات.
- يوجد جدول `private.admin_users` لكنه يدعم حاليًا دورًا واحدًا فقط (`admin`).
- يوجد جدول `public.tournaments` ويدعم المنطقة والمدينة، لكنه لا يحتوي حقل دولة.
- جدول `public.players` يحتوي المدينة والمنطقة ولا يحتوي حقل دولة.
- حسابات اللاعبين مرتبطة بـ Supabase Auth عبر `players.auth_user_id`.
- هناك جداول خاصة إدارية وتشغيلية داخل schema `private` تحتاج مراجعة سياسات الوصول قبل توسيع الصلاحيات.

## نموذج الصلاحيات

### المالك `owner`

المالك هو صاحب أعلى صلاحية في النظام، ويستطيع:

- إضافة لاعب.
- تعديل بيانات أي لاعب.
- تعديل نقاط اللاعب.
- حظر اللاعب أو فك الحظر عنه.
- حذف اللاعب نهائيًا.
- إضافة مشرف جديد.
- إلغاء صلاحية مشرف.
- تعديل نطاق عمل المشرف.
- إنشاء وتعديل وإلغاء البطولات.
- مشاهدة سجل الإجراءات الإدارية كاملًا.

لا يمكن لأي مشرف حذف المالك أو تغيير دوره.

### المشرف `moderator`

المشرف يستطيع:

- البحث عن اللاعبين وعرض بياناتهم.
- تعديل بيانات اللاعب المسموح بها.
- تعديل النقاط وفق القيود المعتمدة.
- حظر اللاعب وفك الحظر.
- إدارة البلاغات.
- إنشاء وتعديل وإدارة البطولات ضمن النطاق الممنوح له.

المشرف لا يستطيع:

- إضافة مشرف جديد.
- حذف مشرف.
- ترقية نفسه أو غيره إلى مالك.
- حذف المالك.
- تغيير إعدادات الأمان أو الأدوار العليا.

## نطاق المشرف

يدعم المشرف أحد النطاقات التالية:

- `global`: إدارة تشغيلية على جميع الدول والمدن.
- `country`: إدارة دولة محددة فقط.
- `city`: إدارة مدينة محددة داخل دولة محددة.

حقول النطاق المقترحة في سجل المشرف:

- `scope_type`
- `scope_country`
- `scope_city`

ويجب أن تتحقق جميع العمليات الحساسة من هذا النطاق على الخادم، لا في واجهة المتصفح فقط.

## إدارة اللاعبين

### إضافة لاعب

تتم من لوحة الإدارة عبر نموذج يحتوي على الأقل على:

- الاسم.
- البريد الإلكتروني.
- كلمة مرور أولية أو مسار دعوة آمن.
- الدولة.
- المدينة.
- الجنس إذا كان مستخدمًا في النظام.
- النقاط الابتدائية، والافتراضي 1500.

إنشاء حساب Supabase Auth لا يتم من JavaScript العام في المتصفح بمفتاح `service_role`. العملية يجب أن تمر عبر Edge Function أو مسار خادمي موثوق يتحقق أولًا من أن المنفذ هو المالك أو مشرف مخوّل.

### تعديل اللاعب

يسمح بتعديل:

- الاسم.
- الدولة.
- المدينة.
- الجنس.
- النقاط.
- حالة الحساب.

يجب أن يسجل كل تعديل حساس في سجل الإدارة مع القيمة السابقة والجديدة والسبب وهوية المنفذ.

### حذف اللاعب

الحذف النهائي عملية خاصة بالمالك فقط.

التدفق المقترح:

1. فتح ملف اللاعب.
2. اختيار "حذف اللاعب".
3. إظهار تحذير واضح بأن الحذف نهائي.
4. طلب سبب الحذف.
5. تأكيد ثانٍ.
6. تنفيذ الحذف خادميًا.
7. تنظيف أو معالجة العلاقات التابعة حسب سياسة البيانات.
8. حذف حساب Supabase Auth المرتبط بعد معالجة البيانات التابعة.
9. تسجيل العملية في سجل تدقيق مستقل لا يعتمد على بقاء صف اللاعب.

بسبب وجود علاقات كثيرة مع `players`، لا يجوز تنفيذ `DELETE` مباشر قبل تحديد سياسة واضحة لكل جدول تابع. بعض السجلات التاريخية مثل نتائج المباريات وسجل النقاط قد تحتاج الاحتفاظ بها مع إخفاء هوية اللاعب بدل حذفها بالكامل.

## إدارة المشرفين

يتم توسيع `private.admin_users` ليشمل:

- `role`: بقيم `owner` أو `moderator`.
- `scope_type`.
- `scope_country`.
- `scope_city`.
- `is_active`.
- `created_by`.
- `created_at`.

### إضافة مشرف

المالك فقط يستطيع إضافة مشرف.

التدفق:

1. البحث عن المستخدم المسجل بالبريد الإلكتروني أو معرف الحساب.
2. اختيار الدور `moderator`.
3. اختيار النطاق: عالمي أو دولة أو مدينة.
4. حفظ الصلاحية.
5. تسجيل الإجراء في سجل الإدارة.

لا يتم الاعتماد على `user_metadata` لتحديد الصلاحيات. المصدر المرجعي للصلاحية يكون جدولًا إداريًا خاصًا أو `app_metadata` تُحدّث خادميًا عند الحاجة.

## إدارة البطولات

يتم تطوير `public.tournaments` بدل إنشاء نظام موازٍ جديد.

### الحقول المقترحة

- `id`
- `name`
- `scope_type`: `global`, `country`, `city`
- `country`
- `region` عند الحاجة للتوافق الحالي
- `city`
- `time_control`
- `starts_at`
- `registration_opens_at`
- `registration_closes_at`
- `max_players`
- `status`: `draft`, `open`, `running`, `finished`, `cancelled`
- `created_by`
- `created_at`

### قواعد النطاق

- بطولة عامة: لا تشترط دولة أو مدينة.
- بطولة دولة: `country` إلزامية و`city` فارغة.
- بطولة مدينة: `country` و`city` إلزاميتان.

لا يعتمد قبول اللاعب على النص الظاهر في الصفحة فقط؛ يجب التحقق في قاعدة البيانات من أن دولة ومدينة اللاعب تطابقان نطاق البطولة عند التسجيل.

### تسجيل اللاعبين في البطولات

إضافة جدول وسيط مقترح:

`public.tournament_registrations`

ويحتوي مثلًا على:

- `tournament_id`
- `player_id`
- `status`
- `registered_at`
- قيد فريد على `(tournament_id, player_id)`

مع RLS وسياسات تمنع لاعبًا من تسجيل لاعب آخر أو التسجيل في بطولة لا تطابق نطاقه الجغرافي.

## الدولة والمدينة

يضاف حقل `country` إلى `public.players` وإلى `public.tournaments`.

يجب الحفاظ على البيانات الحالية وعدم كسر اللاعبين الموجودين. الانتقال يكون تدريجيًا:

- السماح مؤقتًا بقيمة `NULL` للاعبين الحاليين.
- استكمال الدولة عند أول تعديل للملف أو عبر عملية تحديث مدروسة.
- عدم فرض `NOT NULL` إلا بعد اكتمال البيانات القديمة إن لزم.

## الأمان

### العمليات الحساسة

لا يسمح للواجهة العامة بتنفيذ أي من التالي مباشرة بصلاحية العميل العادي:

- إنشاء مستخدم Auth إداريًا.
- حذف مستخدم Auth.
- إضافة أو حذف مشرف.
- تغيير دور إداري.
- حذف لاعب نهائيًا.

تتم هذه العمليات عبر Edge Function محمية أو مسار خادمي مكافئ مع التحقق من الجلسة والدور والنطاق.

### RLS

يجب مراجعة جداول `private` قبل التوسعة، لأن فحص المشروع الحالي أظهر جداول خاصة بدون RLS. لا يتم تشغيل RLS بشكل أعمى دون سياسات، لأن ذلك قد يوقف النظام الحالي. يتم أولًا تحديد طرق الوصول الحالية ثم إضافة السياسات واختبارها.

### سجل الإدارة

يجب توسيع سجل الإدارة ليشمل أنواعًا إضافية مثل:

- `player_create`
- `player_update`
- `player_delete`
- `player_ban`
- `player_unban`
- `rating_change`
- `moderator_create`
- `moderator_update`
- `moderator_remove`
- `tournament_create`
- `tournament_update`
- `tournament_cancel`

ويحتفظ السجل بهوية المنفذ والهدف والسبب والوقت والقيم السابقة والجديدة عند الحاجة.

## واجهة لوحة الإدارة

تضاف أقسام واضحة في القائمة الجانبية:

- الرئيسية.
- اللاعبون.
- المشرفون — للمالك فقط.
- البطولات.
- المباريات.
- البلاغات.
- سجل الإدارة.

### شاشة اللاعبين

- زر "إضافة لاعب".
- بحث وفلاتر حسب الدولة والمدينة والحالة.
- ملف لاعب مفصل.
- تعديل البيانات والنقاط.
- حظر/فك الحظر.
- زر حذف نهائي يظهر للمالك فقط.

### شاشة المشرفين

- قائمة المشرفين.
- إضافة مشرف.
- تحديد دولة أو مدينة أو جميع الدول.
- تعطيل أو إلغاء الإشراف.

### شاشة البطولات

- زر "إضافة بطولة".
- اختيار نوع البطولة: عامة / دولة / مدينة.
- اختيار الدولة.
- اختيار المدينة عند الحاجة.
- تحديد التاريخ والزمن والحد الأقصى للاعبين.
- فتح وإغلاق التسجيل.
- عرض عدد المسجلين.
- تعديل أو إلغاء البطولة حسب الصلاحية.

## تدفق البيانات

الواجهة الإدارية لا تقرر الصلاحية بنفسها. كل طلب إداري يمر بالمراحل التالية:

1. جلسة Supabase صالحة.
2. تحديد المستخدم الإداري من جدول الصلاحيات الخاص.
3. التحقق من الدور.
4. التحقق من النطاق الجغرافي عند الحاجة.
5. تنفيذ العملية.
6. تسجيل العملية في سجل الإدارة.
7. إعادة النتيجة للواجهة.

## التعامل مع الأخطاء

- إذا انتهت الجلسة: إعادة المستخدم إلى تسجيل الدخول.
- إذا كانت الصلاحية غير كافية: رفض العملية برسالة واضحة دون كشف تفاصيل حساسة.
- إذا تعارض حذف اللاعب مع علاقات تاريخية: منع الحذف وإظهار سبب قابل للمعالجة بدل حذف جزئي.
- إذا لم تطابق دولة أو مدينة اللاعب نطاق البطولة: رفض التسجيل.
- إذا حاول مشرف إدارة مشرف آخر: رفض الطلب خادميًا حتى لو تم تزوير طلب المتصفح.

## الاختبارات المطلوبة

### صلاحيات

- المالك يستطيع إضافة وحذف مشرف.
- المشرف لا يستطيع إضافة أو حذف مشرف.
- المشرف المقيد بدولة لا يستطيع إدارة لاعب أو بطولة خارج دولته.
- المشرف المقيد بمدينة لا يستطيع إدارة بيانات خارج مدينته.

### اللاعبين

- إنشاء لاعب ينشئ Auth + player بشكل متسق.
- فشل أي خطوة لا يترك حسابًا نصف منشأ.
- حذف لاعب يتعامل مع العلاقات التابعة وفق السياسة المعتمدة.
- تعديل النقاط يسجل القيمة السابقة والجديدة.

### البطولات

- بطولة الدولة تقبل لاعبي الدولة فقط.
- بطولة المدينة تقبل لاعبي المدينة المحددة فقط.
- لا يمكن التسجيل بعد إغلاق التسجيل.
- لا يمكن تسجيل اللاعب مرتين.

### أمان

- مستخدم عادي لا يستطيع استدعاء وظائف الإدارة الحساسة.
- لا يوجد `service_role` أو secret key في ملفات الواجهة العامة.
- جميع العمليات الإدارية الحساسة تسجل في سجل الإدارة.

## الملفات والمكونات المتوقع تعديلها

- `admin.html`
- `admin.js`
- مخطط Supabase عبر migration جديدة
- `private.admin_users`
- `private.admin_actions`
- `public.players`
- `public.tournaments`
- جدول جديد `public.tournament_registrations`
- Edge Function أو وظائف خادمية آمنة لإدارة Auth والعمليات الإدارية الحساسة
- اختبارات لوحة الإدارة والصلاحيات

## قرارات معتمدة

- يوجد مالك واحد بصلاحيات كاملة.
- المشرفون بصلاحيات أقل من المالك.
- المشرف لا يستطيع إضافة أو حذف مشرفين.
- المالك يستطيع إضافة لاعب وحذفه نهائيًا.
- البطولات يمكن أن تكون عامة أو حسب الدولة أو حسب المدينة داخل الدولة.
- يتم تطوير نظام البطولات الموجود بدل إنشاء نظام منفصل.

## خارج النطاق في هذه المرحلة

- نظام دفع للبطولات.
- جوائز مالية آلية.
- تصنيف اتحادي خارجي.
- نظام فرق أو أندية.
- بث مباشر مخصص للبطولات.

هذه العناصر يمكن إضافتها لاحقًا دون تغيير نموذج الصلاحيات الأساسي.
